# DevPod disk-space triage and cleanup

Use this runbook when a Linux DevPod is low on disk space. Start with the
read-only discovery commands and delete only data whose owner and purpose you
understand. Do not run broad recursive deletion commands against a workspace,
home directory, or shared mount.

## 1. Confirm what is full

```bash
df -h && echo && du -xhd1 / 2>/dev/null | sort -h
```

Then check filesystem types and inode pressure:

```bash
df -hT
df -ih
findmnt -D
```

`df -hT` finds byte pressure; `df -ih` finds inode exhaustion, which can make a
filesystem appear to have free capacity while still rejecting new files. Record
the full mountpoint before investigating usage.

## 2. Locate the largest directories

Run these first. They do not delete anything.

```bash
du -xhd1 / 2>/dev/null | sort -h

for path in "$HOME" /workspaces /workspace /tmp /var/tmp /var/lib; do
  [ -d "$path" ] && du -xhd1 "$path" 2>/dev/null | sort -h
done
```

For a single large directory, drill down one level at a time:

```bash
du -xhd1 /home 2>/dev/null | sort -h
du -xhd1 /var 2>/dev/null | sort -h
du -xhd1 <large-directory> 2>/dev/null | sort -h
find <large-directory> -xdev -type f -size +500M -printf '%10s %p\n' 2>/dev/null | sort -n
```

To list the 50 largest files on the DevPod filesystem:

```bash
find / -xdev -type f -printf '%s\t%p\n' 2>/dev/null \
  | sort -nr \
  | head -50 \
  | numfmt --field=1 --to=iec
```

When available, `ncdu` is the quickest interactive way to inspect the same
filesystem without crossing into mounted volumes:

```bash
ncdu -x /
```

If space was deleted but not returned, identify processes still holding deleted
files open. Restart only the owning process after confirming its purpose:

```bash
lsof +L1 2>/dev/null
```

## 3. Check common DevPod consumers

### Docker or container build cache

```bash
docker system df -v
docker builder du
```

If the output shows disposable build cache, remove old cache interactively:

```bash
docker builder prune --filter until=168h
```

For stopped containers and dangling images only, review Docker's report and use
the interactive prunes below as needed:

```bash
docker container prune
docker image prune
```

Do **not** run `docker system prune --volumes` without confirming that no needed
DevPod, database, or test data is stored in Docker volumes.

### Language and package-manager caches

Inspect only caches that exist in the DevPod:

```bash
du -sh "$HOME"/.cache "$HOME"/.npm "$HOME"/.local "$HOME"/.cargo "$HOME"/.rustup \
  "$HOME"/.pnpm-store "$HOME"/.local/share/pnpm/store "$HOME"/.vscode-server \
  "$HOME"/.config/Code "$HOME"/go/pkg "$HOME"/.cache/pip \
  "$HOME"/.cargo/registry "$HOME"/.gradle/caches 2>/dev/null

command -v npm >/dev/null && npm cache verify
command -v pnpm >/dev/null && pnpm store status
command -v pip >/dev/null && pip cache info
```

Then use the matching package manager to clean only its own cache:

```bash
command -v npm >/dev/null && npm cache clean --force
command -v pnpm >/dev/null && pnpm store prune
command -v pip >/dev/null && pip cache purge
command -v yarn >/dev/null && yarn cache clean
```

These commands may require downloads on the next build; they should not remove
project source or lockfiles.

If `$HOME/.cache` is confirmed to contain only disposable cache data, inspect
the immediate contents, then clear it explicitly:

```bash
find "$HOME/.cache" -mindepth 1 -maxdepth 1 -printf '%f\n' 2>/dev/null | sort
rm -rf -- "$HOME"/.cache/*
```

Do not run the removal command if the inspection shows a cache that must be
preserved, or if the DevPod uses a shared home directory.

### Git repositories and worktrees

Check repository and worktree size before doing anything:

```bash
git worktree list
git count-objects -vH
git clean -ndX
```

`git clean -ndX` is a dry run that lists ignored build output. Review it
carefully. Only if every listed path is disposable build/cache output, repeat
with `-fdX` from the intended repository root:

```bash
git clean -fdX
```

Never use `git clean -fdx` casually: it also removes untracked, non-ignored
files and can delete local work.

### Logs and temporary files

```bash
journalctl --disk-usage 2>/dev/null
du -sh /tmp /var/tmp 2>/dev/null
find /tmp /var/tmp -xdev -type f -mtime +7 -printf '%TY-%Tm-%Td %10s %p\n' 2>/dev/null | sort
```

If the DevPod actually uses systemd journal logs and the retention policy allows
it, reclaim old journal entries deliberately:

```bash
journalctl --vacuum-time=7d
```

For `/tmp` and `/var/tmp`, delete only reviewed, old files owned by your user or
known to be generated by a stopped tool. Do not bulk-delete shared temporary
directories in a multi-user DevPod.

## 4. Verify reclaimed capacity

After each bounded cleanup, re-run:

```bash
df -hT
df -ih
docker system df 2>/dev/null || true
```

Record the mountpoint, the category cleaned, capacity before/after, and the
command used. If the full filesystem is a DevPod provider volume, a workspace
mount, or a platform-managed image layer that you do not control, stop after
collecting this evidence and ask the DevPod/platform owner to resize or rebuild
the correct resource.

## Recommended first pass

For a typical development DevPod, run this sequence before deleting anything:

```bash
df -hT
df -ih
docker system df -v 2>/dev/null || true
du -xhd1 "$HOME" 2>/dev/null | sort -h
du -xhd1 /workspaces 2>/dev/null | sort -h
git clean -ndX
```

This separates a full provider volume, Docker cache, package cache, workspace
build output, and inode pressure without risking project data.
