Exposing AKS applications over Azure Private Link

Private connectivity from other VNets, other subscriptions, other tenants and Azure Databricks into applications running on AKS — with no public endpoint anywhere on the path.

Verified 2026-07-30 Sources: Microsoft Learn + cloud-provider-azure 27 corrections to working notes Status: not yet live-validated

✓ Verdict — deployable today, first-party only

The whole path is Microsoft-supplied: Private Endpoint → Private Link Service → Standard internal load balancer → Istio ingress gateway → Pods. No custom components, no third-party products, nothing to build. The Private Link Service is created declaratively from Kubernetes by annotating a Service.

Traffic is not dropped after five minutes. The timers on this path are idle timeouts, not connection lifetime caps — active connections stay up indefinitely.

Scope of this review: documentation and architecture only. Every claim is sourced to Microsoft Learn, but nothing here has been validated against a live deployment. A small proof of concept — one Private Link Service, one Databricks NCC rule, one query end to end — is what turns this from sourced into proven.

The questions that were asked

Short answers

Can we deploy this?

Yes

Every component is generally available. The pattern is documented by Microsoft for exactly this use case, including Databricks as a consumer.

Do we need to build anything, or buy third-party?

No

100% first-party. The only open source involved is Envoy/Istio inside the cluster, and Microsoft ships and supports that as a managed add-on.

Will traffic drop after 5 minutes?

No

Idle timeout, not a lifetime cap. Any byte in either direction resets it. One keepalive setting covers the silent-socket edge case.

Control plane and data plane are separate problems

A frequent source of confusion in the working notes. A private cluster does not make your applications private, and private applications do not require a private cluster. These two lanes share nothing.

Lane 1 · control plane

kubectl, ARM, GitOps

  • Reached via Bastion, VPN, ExpressRoute or a self-hosted agent
  • --enable-private-cluster (uses Private Link), or API Server VNet Integration (uses neither Private Link nor a tunnel)
  • Optionally --disable-public-fqdn
  • Carries zero application traffic
Lane 2 · data plane

Application traffic — what we are building

  • Private Endpoint → Private Link Service → internal LB → Istio → Pods
  • Works whether or not the cluster is private
  • No VNet peering required for consumers
  • Crosses subscriptions and tenants

The five-minute question, answered properly

Two idle timers — and the load balancer's is the tighter one

Both timers watch for silence, not elapsed connection age. Any byte in either direction resets them, but any connection without bytes or keepalives can expire — including an idle pool entry, a quiet stream, or a request waiting silently for a response.

TimerDefaultTunable?How
Standard load balancer rule 4 min (240s) yes azure-load-balancer-tcp-idle-timeout
4–30, integer minutes
Private Link Service ~5 min (300s) no Not exposed. Fixed platform behaviour.

Four levers, all managed-service configuration

Lever 1 — most robust

Cap client pool idle time

  • Evict idle sockets at 120–180s to avoid reusing connections that may have expired
  • The only lever that works on Databricks serverless, where you cannot set host socket options
Lever 2

Application keepalive

  • HTTP/2 PING, gRPC keepalive_time, or a cheap heartbeat
  • Keeps the connection genuinely non-idle rather than racing the timer
Lever 3

Raise the LB timer

  • azure-load-balancer-tcp-idle-timeout: "30"
  • Removes one timer. Does not remove the problem — do this and lever 1
Lever 4

Fail fast, retry

  • Retain AKS's default TCP reset-on-idle behavior so expiry gives an RST instead of a hang
  • Retry idempotent requests on connection reset — with two timers, occasional resets are normal

Deliberately not recommended: OS-level SO_KEEPALIVE / TCP_KEEPIDLE on the gateway's downstream listener. That needs an EnvoyFilter, which sits outside the Istio add-on's allow-listed customizations — the same wall as PROXY protocol. The four levers above are sufficient.

Choosing a pattern

Which one do you actually need?

Four patterns exist. Most teams need only one, and plenty legitimately stop at the simplest.

If…PatternPrivate Link?Notes
Consumers are in your own VNet or already-peered VNets 4 — internal ingress only No Simplest. Many enterprises stop here, and that is a valid answer.
Consumers span subscriptions or tenants, or are Databricks serverless, and you want to avoid peering 2 — PLS + internal LB + Istio recommended Yes What this document describes. Consumers create a private endpoint; no routing changes.
You need a WAF in front, consumers still private 3 — App Gateway Private Link Yes Needs a dedicated Private Link subnet with network policies disabled. WAF is a SKU of App Gateway, not a separate hop.
You want a public internet edge with a private origin Front Door Premium private-link origin Yes, to origin caution Re-introduces a public endpoint. No mTLS to private-link origins. Wrong tool for Databricks→AKS.
Only the control plane needs to be private 1 — private API server Yes, or VNet Integration Orthogonal to all of the above. Does nothing for application traffic.

Azure Databricks

Three traffic directions — do not conflate them

"Expose applications over Private Link into our Kubernetes clusters" splits into three different Azure features depending on who is calling whom. Direction A is the one that was asked for.

Direction A · primary path

Databricks serverless → your AKS app

  • SQL warehouses, jobs, notebooks, pipelines, model serving
  • NCC private endpoint rule targeting your Private Link Service resource ID
  • Plus domain_names — and this is where the .internal trap bites
  • You approve the pending connection on the PLS
Direction B

Databricks classic → your AKS app

  • VNet-injected workspace clusters
  • Ordinary private endpoint in a routable VNet
  • If VNets are already peered you can skip Private Link entirely and hit the internal LB
Direction C · different feature

Your AKS pods → Databricks

  • Calling the Databricks REST API or SQL endpoints privately
  • Private endpoint, sub-resource databricks_ui_api
  • This is Databricks front-end/back-end Private Link. Nothing to do with your PLS.

Before you start

Seven traps, two of which stop the build dead

01An internal-LB annotation alone does not create a Private Link Serviceblocker

The working notes show a Service with only azure-load-balancer-internal: "true" and claim Azure "then creates" a PLS. It does not — you get an internal load balancer and nothing else. Nothing creates a PLS implicitly.

Fix: add service.beta.kubernetes.io/azure-pls-create: "true".

02Databricks rejects private-use TLDsblocker

.internal, .localhost and .test are not accepted in NCC private endpoint rules. Both draft documents use api.company.internal, which would fail at rule creation.

Fix: use a registered domain hosted in a private DNS zone, e.g. api.contoso.com.

03Private Link Service is unsupported on nodeIP backend poolssilent

Stay on the AKS default nodeIPConfiguration. The incompatibility is not loudly signposted, so verify it rather than assume it.

04DNS has two different consumer contractsongoing

For a consumer-owned endpoint to a customer PLS, no privatelink.* zone or zone group is created automatically. Maintain an A record to that endpoint's private IP in each consumer VNet.

Databricks owns the serverless endpoint. Its NCC domain_names must instead resolve directly to addresses represented in the load balancer backend pool; do not point them at a Databricks-managed PE IP or rely on DNS chasing.

05The source IP is always the PLS NAT IPdesign

Private Link Service always destination-NATs. Your application never sees the consumer's IP. Allowlists must permit the PLS NAT subnet — never "the Databricks IPs".

Recovering the real client IP needs PROXY protocol v2, which then breaks every backend that does not parse it, health probes included. Derive identity from mTLS or JWT, not from the network.

06Pin the PLS name, or upgrades orphan your consumerslifecycle

The PLS binds to the load balancer frontend IP configuration, not to the Service. An Istio add-on minor-revision upgrade creates a second gateway Service and frontend. When a Service is deleted the PLS may survive, active connections drop, and consumer private endpoints become obsolete — and Azure will not clean them up for you.

Fix: set azure-pls-name and azure-pls-resource-group explicitly, grant the AKS control-plane identity Network Contributor on that custom resource group, and write a PE-cleanup runbook. Without that grant, use the node resource group.

07azure-pls-* is not in the Istio add-on's documented annotation setpath choice

The add-on documents a specific supported annotation list for its managed aks-istio-ingressgateway-internal Service, and no PLS annotation appears on it. Use the Gateway API spec.infrastructure.annotations route, a self-managed gateway Service, or create the PLS out-of-band against the load balancer frontend.

Provider side

What the Service actually looks like

The entire Azure-side build is this manifest. Before applying it, grant the AKS control-plane identity Network Contributor on rg-platform-network; its default Contributor grant covers only the node resource group. Applying the manifest creates the internal load balancer and Private Link Service. 

apiVersion: v1
kind: Service
metadata:
  name: ingress-internal
  namespace: platform-ingress
  annotations:
    service.beta.kubernetes.io/azure-load-balancer-internal: "true"
    service.beta.kubernetes.io/azure-load-balancer-internal-subnet: "ilb-subnet"
    # Without this line you get an internal LB and no Private Link Service.
    service.beta.kubernetes.io/azure-pls-create: "true"
    # Pin the identity so revision upgrades don't orphan consumer endpoints.
    service.beta.kubernetes.io/azure-pls-name: "pls-aks-platform-ingress"
    service.beta.kubernetes.io/azure-pls-resource-group: "rg-platform-network"
    # Dedicated NAT subnet. Required if externalTrafficPolicy is Local.
    service.beta.kubernetes.io/azure-pls-ip-configuration-subnet: "pls-nat-subnet"
    service.beta.kubernetes.io/azure-pls-ip-configuration-ip-address-count: "8"
    # Subscription list, or "*" if you need auto-approval (a real trade-off).
    service.beta.kubernetes.io/azure-pls-visibility: "<consumer-sub-id> <databricks-sub-id>"
    # Move the LB idle timer out of the way; the fixed PLS 300s still binds.
    service.beta.kubernetes.io/azure-load-balancer-tcp-idle-timeout: "30"
    service.beta.kubernetes.io/azure-load-balancer-disable-tcp-reset: "false"
spec:
  type: LoadBalancer
  selector:
    istio: platform-ingress
  ports:
    - name: https
      port: 443
      targetPort: 8443

Pre-flight

Non-negotiables

  • AKS load balancer backend pool type is nodeIPConfiguration (the default). PLS is unsupported on nodeIP.
  • Dedicated PLS NAT subnet, privateLinkServiceNetworkPolicies Disabled, 8+ free IPs, same VNet as the backend pool, different from the pod subnet.
  • PLS pinned by name and resource group so revision upgrades don't orphan consumer endpoints; AKS control-plane identity has Network Contributor on that custom resource group.
  • A real registered domain for consumer hostnames — never .internal.
  • DNS path documented per consumer: consumer-owned PE uses A records to its PE IP; Databricks serverless uses NCC names resolving directly to LB backend addresses.
  • Idle-timeout hygiene in consumer onboarding: pool eviction under ~240s, app keepalive, LB timer raised, AKS TCP reset default retained, retry on reset.
  • Identity from mTLS or JWT, never from source IP.
  • Manual private endpoint approval as the platform gate. Auto-approval only if you accept visibility: "*".
  • Runbook for private endpoint cleanup when a Service or PLS is deleted — Azure will not do it.
  • Certificate SANs cover every hostname registered in every Databricks NCC rule.
