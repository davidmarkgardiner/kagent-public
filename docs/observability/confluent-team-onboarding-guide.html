01 · current pattern

What our triage path does

For Kubernetes events and selected logs, Alloy collects evidence; Vector filters, normalizes, redacts and publishes to Confluent Kafka; an Argo Events Kafka EventSource consumes records and a Sensor starts a bounded triage Workflow. The workflow calls a read-only kagent agent.

Evidence level. The repo records a July 2026 homelab test using real Confluent Cloud: a Vector-published event was consumed by Argo and produced a triage workflow. That does not verify today's workplace cluster, forms, permissions, or team onboarding. See the replication bundle and workplace onboarding note.

Our broader design keeps metric alerts owned by the Alertmanager lane and events/log evidence owned by the Vector lane. It does not ask each team to join the kagent triage topic. A new team normally receives its own topic, group, service identities and ACLs on the approved shared Kafka cluster.

02 · mental model

What is actually separate?

Cluster / bootstrap endpoint

The shared Kafka service and network destination. The platform team supplies the approved endpoint and connectivity path. A shared endpoint does not imply shared data permissions.

Topic

The named stream of records, retention and partitioning policy. A dedicated topic gives the new team a clean data contract and a practical ACL boundary.

Consumer group

A stable read cursor and work-sharing identity. Replicas in one group divide partitions; a different group tracks its own offsets and can read the same topic independently if authorized.

Do not confuse independent offsets with isolation. A new group on our triage topic can still read that topic if its principal has permission. For a separate use case, request a dedicated topic plus a dedicated group and least-privilege service account. A consumer group does not filter content or deduplicate two records about one incident.

A producer writes a topic; it does not need a consumer group. A consumer reads a topic as a group. For Confluent Cloud ACLs, a producer needs topic write permission; a consumer needs topic read and group read permission. Separate producer and consumer credentials are preferable when both roles are needed.

03 · team choice

How could another team integrate?

The team should describe its problem and choose clients based on the workload. These are examples, not mandatory platform components.

NeedProduce to KafkaConsume from KafkaGood fit / consideration
Logs, events and telemetryVector Kafka sink, as in our triage pathVector Kafka source, Argo Events, or an application clientVector is useful for filtering, redaction and formatting before publish. Verify actual broker delivery, not only local buffering.
Trigger a Kubernetes workflowAny schema-compatible producerArgo Events Kafka EventSource → Sensor → WorkflowGood when each accepted record should start a controlled Kubernetes action. Add validation, idempotency and concurrency limits.
Application events or commandsKafka client SDK in Java, Go, Python, .NET or JavaScriptKafka client SDK with a stable group IDBest when the application owns serialization, retries, offsets and business processing.
Move data to or from a supported systemManaged source connectorManaged sink connectorReview available connector, ownership, cost and data classification with the platform team.
Join, aggregate or reshape streamsExisting sources or an applicationFlink SQL or Kafka Streams, often writing a new output topicUseful for stateful transformations; needs its own schema and output access.

Ask first: what event is produced, who owns it, who consumes it, what happens on duplicates, and whether a historical replay is acceptable. Choose retention, partitions and schema based on those answers, not on the tool name.

04 · request sequence

What goes into the work forms?

Our existing onboarding note refers to an onboard producer/topic form and an add consumer group form. Exact workplace field labels and identity-pool behavior need confirmation with the Kafka platform owner.

Producer / topic form

  • Owning team, support contact and business purpose
  • Requested {{TEAM_TOPIC}} and approved naming prefix
  • Producer application / workload identity
  • Message sample, schema version, key and sensitive-data classification
  • Expected throughput, message size, retention and partition needs
  • Environment and network location

Platform output: approved topic, schema rules, producer principal and write ACL.

Consumer group form

  • Requested stable {{TEAM_CONSUMER_GROUP}}
  • Consumer application and owning service identity
  • Exact topic or topics to read
  • First-start offset: new messages or approved bounded replay
  • Expected replicas, processing latency and lag alert owner
  • Error path, retries, dead letter handling and idempotency

Platform output: group registration/permission, topic read ACL and approved credential delivery.

Permission sketch: {{TEAM_PRODUCER_PRINCIPAL}} → write {{TEAM_TOPIC}}; {{TEAM_CONSUMER_PRINCIPAL}} → read {{TEAM_TOPIC}} and read {{TEAM_CONSUMER_GROUP}}. The platform decides whether its portal uses ACLs, RBAC, identity pools or a combination.

05 · platform handoff

What we give the team

  1. Confirmed Kafka bootstrap endpoint and the network path from their runtime.
  2. Approved topic and group names, schema/serialization contract and initial offset choice.
  3. Scoped producer and/or consumer credentials through the workplace secret delivery mechanism; never in the GitLab ticket, this HTML file, source control or chat.
  4. TLS/SASL connection profile or equivalent approved authentication instructions.
  5. A disposable smoke-test scope and a platform contact for ACL, lag and schema errors.
Their integration remains theirs. They choose and operate the producer and consumer tooling, deployment, offset handling and business behavior. We provision and verify the Kafka boundary agreed in the forms.
06 · proof

Safe acceptance test

Use a dedicated test topic or approved marker on the new topic. Configure the Confluent CLI through the approved local profile or secret store; do not put API secrets into the command line or ticket. Start the consumer first with an authorized temporary group, then produce one synthetic marker. Replace placeholders only in your private session.

# Terminal A — separate, authorized smoke group (not the production group)
confluent kafka topic consume {{TEAM_TOPIC}} \
  --group {{TEAM_SMOKE_GROUP}}

# Terminal B — type a synthetic JSON marker; then Ctrl-D
confluent kafka topic produce {{TEAM_TOPIC}}
{"schema_version":"{{SCHEMA_VERSION}}","test_id":"{{UNIQUE_TEST_ID}}","kind":"onboarding-smoke"}

This assumes the CLI is already logged into the approved environment/cluster and uses credentials with the required topic and group access. If the topic requires Schema Registry serialization or validation, use its approved schema-aware producer instead of the plain JSON line. The CLI is interactive; check its displayed prompt and accepted syntax before typing.

  1. Confirm the producer acknowledges the record and record its topic, partition and offset.
  2. Confirm the consumer receives the same test_id once in the intended group.
  3. Confirm production consumer lag and downstream action only if that integration is part of the request.
  4. Remove or expire the smoke group/credential under platform policy; retain redacted evidence in the onboarding ticket.
Replay caution. A new production group has no committed offsets. Do not switch it to oldest/from-beginning on an incident topic without an approved replay plan. Consumer delivery and workflow side effects may repeat; use a stable event ID and idempotent downstream handling.
