Give our agents a map.

Neo4j graph memory for kagent: what it is, where it helps, what our Kubernetes lab proved, and the integration we recommend.

Decision in one sentenceAdopt a narrow, read-only graph context source for incident triage. Keep live cluster state authoritative and make the graph optional.

01 · The idea

Neo4j stores relationships as first-class data.

Nodes

Services, workloads, incidents, changes and runbooks each have a stable identity and useful properties.

Example · demo/inventory

Directed links

Explicit edges say DEPENDS_ON, ORIGINATED_AT or RESOLVED_USING. Queries follow these paths in either direction.

Example · checkout → catalog → inventory

For our team, the valuable question is: “If inventory has a problem, who depends on it, and what happened before?”

03 · Integration

Two sources. One grounded answer.

1 · Live signalKubernetes API says what is happening to a workload now.
→
2 · Graph contextNeo4j supplies dependency paths and curated historical links.
→
3 · Bounded toolsFixed, read-only MCP queries pass through agentgateway.
→
4 · kagent responseThe agent separates observed state, potential impact and past incidents.

Authoritative now

Kubernetes readiness, scheduling, events, metrics and logs. Recheck at answer time.

Curated memory

Service dependencies, incident lessons, ownership and Git runbook references. Track provenance and freshness.

Graph writes belong to a controlled curation workflow. Triage agents get read tools only; execution permissions stay with governed workflows.

04 · The lab test

Same alert. Same model. Different context.

We deliberately made a synthetic demo-inventory pod unschedulable in a local kind cluster, then asked two Kimi-backed kagent agents the same question.

Kubernetes only

0/1 Ready. Pod Pending.

Correctly identified the scheduling failure. Could not verify downstream services, a related prior incident or the current runbook.

It also speculated about a Neo4j dependency from a namespace name. That inference was unsupported.

Kubernetes + Neo4j

Same live fault, richer context.

Named catalog and checkout as potential dependents, plus the resolved incident and current successor runbook.

It said the old cache change did not explain this new scheduling fault.

Synthetic local POC, 29 September 2026. Both answers were completed A2A turns; runtime and gateway logs showed the tool calls.

06 · Evidence boundary

Useful context is proven. Operational uplift is not.

What the POC establishedWhat it has not established
kagent can combine live Kubernetes status with bounded Neo4j reads through agentgateway.Faster incident resolution, lower MTTR or better decisions in a real on-call shift.
Stored paths correctly identified potential catalog and checkout impact.That catalog or checkout were actually unhealthy; only inventory was observed live.
Historical links, ambiguity, empty results and a backend outage were handled without inventing graph IDs.A production ingestion pipeline, provenance policy, backup/restore, high availability or access model.
One bounded synthetic scenario produced a stronger answer than Kubernetes-only.That Neo4j beats relational tables and recursive queries on cost or quality.

The first run missed dependents because a tool walked the edge in the wrong direction. We fixed the reverse query and reran the same question. This is a useful reminder to test the actual question, not just tool availability.

07 / 10
07 · Engineering trade-off

A graph is valuable only if we keep it trustworthy.

What we would operate

  • Another stateful database, with backup and recovery
  • Curated ingestion from service inventory, incidents and Git
  • Stable IDs, edge direction, provenance and expiry
  • Monitoring for missing or stale relationships

What we would constrain

  • Fixed, parameterised, bounded MCP read tools
  • No arbitrary Cypher or graph writes for triage agents
  • Live Kubernetes checks before current-state claims
  • Graceful answers when Neo4j is unavailable

The lab used Neo4j Community Edition and a fixed facade. Its database principal was not a production read-only authorization boundary; production security needs a separate design and validation.

08 / 10
08 · Recommendation

Integrate narrowly. Prove value in a canary.

Proposed scope

Opt-in read-only graph context for incident triage: service dependents, relevant historical incidents and current runbook references.

No platform-wide dependency and no agent graph-write capability.

Before broader use

  1. Populate relationships from authoritative sources with provenance and expiry.
  2. Test real incident questions against the current PostgreSQL relationship design.
  3. Measure answer correctness, time saved, stale-data rate and operational cost.

Decision for the team: approve a bounded integration path, with the graph optional and live Kubernetes evidence authoritative.
