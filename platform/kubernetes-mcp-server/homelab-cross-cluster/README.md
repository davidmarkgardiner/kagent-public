# Homelab cross-cluster Kubernetes MCP proof

This bundle is a bounded, reversible proof for
[`containers/kubernetes-mcp-server`](https://github.com/containers/kubernetes-mcp-server).
It runs one MCP server in the designated Kind homelab, gives that server a
two-entry runtime kubeconfig backed only by short-lived ServiceAccount
`TokenRequest` credentials, and proves native read-only routing to the local
and remote homelab clusters.

The client sees only these public-safe aliases:

- `red-homelab` — exactly one node
- `proxmox-homelab` — exactly three nodes

This is a non-production POC. It does not register the server with kagent or
agentgateway, expose an external endpoint, alter an application workload, or
provide merge, release, or deployment automation.

## Stage boundary

The offline gate is safe for source-review and Build stages:

```sh
bash platform/kubernetes-mcp-server/homelab-cross-cluster/scripts/verify.sh
```

`verify.sh` performs static YAML/TOML/script checks and an in-memory client
fixture. It never invokes `kubectl`, Helm, a TokenRequest, or `live-poc.sh`, and
it does not contact a cluster.

The live command is deliberately separate and is authorized only in the
ticket's Test stage:

```sh
HOST_CONTEXT=kind-homelab \
TARGET_CONTEXT=proxmox-k8s \
bash platform/kubernetes-mcp-server/homelab-cross-cluster/scripts/live-poc.sh
```

Do not run that command outside the explicitly authorized reversible homelab
test. The live script refuses any other context names.

## What the proof creates

The orchestrator creates the same temporary namespace,
`kubernetes-mcp-cross-cluster-poc`, on the two input clusters. This distinct,
deterministic name avoids adopting or deleting resources from other MCP proofs.
Every created object carries
`app.kubernetes.io/part-of=homelab-cross-cluster-poc`.

On both clusters it creates:

- one dedicated `kubernetes-mcp-cross-cluster-reader` ServiceAccount;
- one narrowly defined reader ClusterRole; and
- one matching ClusterRoleBinding.

The ClusterRole is required because namespaces and nodes are cluster-scoped and
the acceptance test covers workloads across namespaces. It grants only
`get`, `list`, and `watch` on namespaces, nodes, pods/status, events,
Deployments, ReplicaSets, StatefulSets, DaemonSets, Jobs, and CronJobs, plus
`get` on pod logs. It grants no Secret, ServiceAccount, RBAC, TokenRequest,
exec, or write permission.

On the host cluster it additionally creates:

- a default-deny ingress NetworkPolicy and a narrow smoke-client allowance;
- a hardened, tokenless MCP Deployment and ClusterIP Service;
- the runtime-only scoped-kubeconfig Secret and server ConfigMap; and
- one labelled, hardened in-cluster client Pod.

No Ingress, HTTPRoute, NodePort, LoadBalancer, host port, or external IP is
created. The Service is `ClusterIP` only.

## Fail-closed sequence

`live-poc.sh` performs these ordered steps:

1. Validate required commands, the two exact input contexts, distinct cluster
   identities, API readiness, TokenRequest discovery/operator authority, the
   expected one/three node shape, and absence of every named POC resource.
2. Record the existing `default/kubectl-mcp` Deployment UID in a private
   mode-0700 temporary directory.
3. Create the labelled POC namespaces and reader RBAC, then apply ingress
   isolation before the MCP server exists.
4. Start the labelled smoke client and prove a TCP connection from that host
   pod to the target Kubernetes API endpoint. The endpoint is never printed or
   retained. A routing failure stops the proof without weakening a firewall,
   route, or CNI.
5. Request two ten-minute ServiceAccount tokens, construct a minimal
   alias-only kubeconfig, create the Secret through a direct pipe, and suppress
   all credential-bearing output.
6. Verify the reader identities independently with positive and negative
   Kubernetes authorization checks.
7. Start the MCP server, initialize Streamable HTTP, list the exact tool
   surface, call `configuration_contexts_list`, and reject any context other
   than the two aliases.
8. Run 20 alternating `resources_list` Node requests. Each result must match
   both the expected cardinality and a controller-owned SHA-256 fingerprint of
   the sorted Kubernetes Node UIDs. The fingerprints are used only in memory
   and are not retained.
9. Prove that `configuration_view`, exec, create/update, delete, and scale tool
   calls are rejected.
10. Remove the local scoped kubeconfig, tear down every owned POC resource,
    verify absence on both clusters, and verify that the preserved
    `default/kubectl-mcp` UID is unchanged.
11. Scan only the bounded temporary evidence with a deterministic redaction
    expression and the repository-local strict JSON schema validator, emit one
    compact public-safe summary, then delete the private temporary directory.

Any unexpected object with the cross-cluster proof's exact namespace or
cluster-scoped RBAC names, context ambiguity, credential/TLS
weakness, permission drift, tool drift, route crossover, scan finding, or
cleanup failure stops the proof. Cleanup is also registered for `EXIT`, `INT`,
and `TERM`.

## MCP and authorization boundaries

[`config/server.toml`](config/server.toml) enables only `core` and `config`,
then applies an explicit tool allowlist. `configuration_contexts_list` is the
only configuration tool. `configuration_view` is disabled and also absent
from the allowlist, so the mounted kubeconfig cannot be requested through MCP.
All mutation, exec, node-log, metrics, Helm, and scale tools are absent.

The MCP tool filter is not treated as authorization. The two reader
ClusterRoles are the Kubernetes API boundary. `verify-rbac.sh` proves allowed
reads and denied Secret, ServiceAccount, RBAC, TokenRequest, `pods/exec`, and
resource-write operations with the actual purpose-issued credentials before
the server starts.

The MCP pod and smoke-client Pod both set
`automountServiceAccountToken: false`. The server authenticates to the target
APIs only through its read-only Secret volume. Both Pods run as non-root with
RuntimeDefault seccomp, no privilege escalation, a read-only root filesystem,
dropped capabilities, and explicit CPU/memory requests and limits.

## Configuration and sensitive values

There are no live environment values in committed manifests. The following
conceptual placeholders exist only at runtime and are never written to Git or
bounded evidence:

| Concept | Source | Retention |
| --- | --- | --- |
| `{{HOST_API_ENDPOINT}}` | selected host context | private temporary memory/file only |
| `{{TARGET_API_ENDPOINT}}` | selected target context | private temporary memory/file only |
| `{{HOST_CA_DATA}}`, `{{TARGET_CA_DATA}}` | flattened selected cluster records | scoped temporary kubeconfig only |
| `{{HOST_TOKEN}}`, `{{TARGET_TOKEN}}` | ten-minute TokenRequests | scoped temporary kubeconfig/Secret only |
| controller Node fingerprints | live Node UIDs | private temporary state only |

The scoped kubeconfig is constructed as JSON (valid kubeconfig YAML) with
exactly two clusters, two token users, and two contexts. It does not merge the
operator's workstation configuration, user credentials, client certificates,
exec plugins, or unrelated contexts. Insecure TLS is rejected and CA data is
required.

Never retain tokens, kubeconfigs, certificates, private endpoints, prompts,
request bodies, raw MCP results, pod logs, or raw Kubernetes API responses.

## Evidence contract

The only live stdout receipt contains:

- the two aliases and their `1`/`3` node counts;
- request count and zero-crossover status;
- allowlist/RBAC pass status;
- ClusterIP-only status;
- teardown and preserved-UID booleans; and
- the honest KindNet NetworkPolicy limitation.

[`evidence/example-summary.json`](evidence/example-summary.json) shows that
schema without representing a live run. The 20-request fixture contains only
aliases, counts, sequence numbers, tool names, and pass/fail states; it is not
a captured API response.

## NetworkPolicy limitation

The host Kind cluster uses KindNet, which does not enforce Kubernetes
NetworkPolicy. The default-deny and labelled-client policies are still applied
before the server starts so the intended boundary is reviewable and portable,
but this proof does not claim that KindNet enforced them. The server remains
ClusterIP-only, and the test must stop rather than replace the CNI or alter
cluster networking.

## Teardown and recovery

`teardown.sh` deletes only the three fixed cross-cluster POC resource names
after verifying their ownership label. It never uses a broad label deletion,
does not inspect or modify the older `kubernetes-mcp-poc` namespace, and never
touches `default/kubectl-mcp`. If an exact-name resource lacks the POC label,
teardown fails closed instead of adopting or deleting it.

After deletion it requires the namespace, ClusterRole, and ClusterRoleBinding
to be absent in both clusters and requires the original `default/kubectl-mcp`
Deployment UID to match. A terminal shell status alone is not considered
successful cleanup.

## Prerequisites

- `bash`, `kubectl`, `jq`, `python3`, `rg`, and `sha256sum`.
- Explicit operator authority for only the temporary POC resources and
  ServiceAccount TokenRequests described above.
- Both authorized kubeconfig contexts already present and healthy.
- Host-pod network reachability to the target API endpoint.
- The existing `default/kubectl-mcp` Deployment present on the host.
- Sufficient time to complete within the ten-minute token lifetime.

The upstream configuration shape and image/chart behavior were reviewed at
source baseline `5d42192b288224d2d0ec7313826f1dd3e144a567`; the deployed image is
the immutable `v0.0.66` release digest shown above.
