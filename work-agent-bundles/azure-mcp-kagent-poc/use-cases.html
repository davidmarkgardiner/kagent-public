02 / PRACTICAL USE CASES

Five questions worth asking.

These are proposed operational scenarios for inventory and activity-log tools. Live Azure results have not yet been tested.

01 · CHANGE CORRELATION Start here

Correlate an outage with Azure changes.

“Did an Azure operation happen around the time these pods lost connectivity?”

AKS-MCP supplies pod events and node evidence. Azure MCP retrieves recent activity-log entries for the named Azure resource. kagent builds a shared timeline.

Useful output: a shortlist of changes to investigate, including timestamps, operation status and evidence gaps.

02 · NODE-POOL INVESTIGATION

Explain a cloud-side operation.

“Was a node-pool update or scaling operation attempted before nodes became unavailable?”

Compare Azure operation status with Kubernetes node conditions and scheduling events. Investigate the named resource and time window.

Useful output: evidence of a relevant operation, plus the next check needed to explain the node symptoms.

03 · RESOURCE INVENTORY

Confirm what exists around the cluster.

“Which network, disk and managed-service resources exist in this resource group?”

List resources in the already-known group to confirm resource names, types and locations before targeting further checks. Inventory alone does not prove a dependency or its health.

Useful output: a scoped inventory and the specific resource that needs investigation.

04 · INCIDENT EVIDENCE PACK

Give the reviewer a coherent timeline.

“Summarise recent Azure operations for this cluster and correlate them with this alert.”

Bring Azure activity-log evidence, supplied Kubernetes observations and the alert into one incident summary. Clearly separate facts from hypotheses.

Useful output: scope, timestamps, operation results, confidence, missing evidence and a proposed next check.

05 · POST-DEPLOYMENT VERIFICATION

Check the cloud-side result of a workflow.

“After the Argo workflow finished, what Azure resources and operations can we confirm?”

Add inventory and activity-log evidence alongside workflow completion and ASO reconciliation. Then use the existing Kubernetes and application checks to verify service health.

Useful output: confirmed Azure observations and a precise list of verification checks still outstanding.

03 / AN INCIDENT WALKTHROUGH

From symptom to reviewable plan.

Illustrative scenario, not a recorded live incident. A recent Azure operation is a lead to investigate, not proof of the cause.

Example trigger

Pods lose connectivity after a period of normal operation.

The incident supplies the cluster, namespace, tenant, subscription, resource group and approximate start time. Missing scope is requested before querying.

  1. Gather Kubernetes evidence

    The AKS specialist checks relevant events, node conditions and workload symptoms through its approved read-only tools.

  2. Confirm the Azure target

    The Azure specialist uses resource inventory in the named group to identify the resource worth examining. It does not guess a subscription or enumerate the fleet.

  3. Inspect recent Azure operations

    Query activity logs for the named resource. Start with a one-hour window and 20 entries; these are proposed prompt budgets, not adapter-enforced limits.

  4. Correlate and explain uncertainty

    kagent compares timestamps and operation status with the symptoms. An operation preceding the outage supports further investigation; it does not establish causation.

  5. Recommend a controlled next step

    Produce the evidence, confidence, proposed check and remediation plan. Any resource change follows human review and the existing Argo or GitOps path.

Evidence boundary: activity logs show control-plane operations. They do not replace pod logs, Grafana, application checks or data-plane telemetry.
