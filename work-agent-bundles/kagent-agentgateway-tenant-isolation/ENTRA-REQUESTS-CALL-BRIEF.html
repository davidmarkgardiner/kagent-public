Meeting brief · read this aloud

Two permissions. Two journeys.

One lets our application call the agent. The other lets the agent use an MCP tool.

The 45-second explanation

“We have two separate calls to secure. First, our AKS application needs permission to call one agent. Second, that agent needs permission to call our MCP API. We are asking the Entra team to set up the identities, API roles and trust so each call can get the right token. We will configure agentgateway to check those tokens, the exact caller identity and the allowed route or tool. Then we will prove both allowed calls work and unapproved calls fail.”

Request 1: how does the app actually reach the agent?

Say this: “The API audience names what the token is for. The gateway URL is where our application sends the HTTP call. They are different things.”

  1. AKS identifies the Pod. Its ServiceAccount supplies a signed Kubernetes token. The UAMI trusts that exact cluster issuer and ServiceAccount through a federated credential.
  2. Entra issues the A2A token. The app exchanges the Kubernetes token for a UAMI access token for the A2A API. The token contains the API audience, UAMI identity and assigned invoke role.
  3. The app calls our gateway URL. It sends the A2A HTTP request with that token in the authorization header. The API audience is not this network address.
  4. The gateway checks and routes. It verifies the token signature, issuer, expiry, audience, role and exact UAMI ID, then forwards to the named Agent Service. A denied call never reaches the agent.

The key boundary

Entra issues tokens with permissions. Agentgateway checks them on every call and limits the exact agent or MCP tool. It normally verifies Entra's signature with public keys; it does not ask Entra to approve each HTTP call.

One important question for the call

“Can your team confirm who creates each API role, who approves and applies the grant, who owns each federated credential, and what IDs and read-backs you will return in the two tickets?”

Note: Every child of the approved blueprint inherits the MCP API role. We still register each child explicitly in the MCP gateway before it may use the route. This inherited-grant design needs a fresh token and gateway test in the work environment.
