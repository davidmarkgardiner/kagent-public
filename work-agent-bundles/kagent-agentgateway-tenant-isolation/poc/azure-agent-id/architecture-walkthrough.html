Identity architecture • visual walkthrough

How an agent gets its own identity

We create a child Agent ID in Entra, grant that child an API role, and plan to let a kagent Pod authenticate through a managed identity. The Gateway checks the resulting token before allowing an MCP tool call.

The important distinction

Creating an Agent ID is not the same as running an agent as that identity. The live PoC proved object creation and a certificate-based token exchange. The production AKS ServiceAccount → UAMI path and automatic token refresh still need implementation and testing.

The complete picture

How it all connects

The upper lane sets up identities and GitOps configuration. The lower lane is the token path a running Pod would use to reach one MCP tool.

Yes, Kubernetes needs federation—but the first federated credential lives on the Azure UAMI. It trusts an OIDC token from the cluster issuer for one exact ServiceAccount subject. Kubernetes holds the ServiceAccount and Pod configuration; it does not store that FIC. The second FIC lives on the Entra blueprint and trusts the UAMI.

01 / cast of characters

Six pieces, six different jobs

Coordinator • proposed

AACM

Receives an approved agent request and would orchestrate Entra/Azure identity setup. We do not yet know its real API. The PoC used direct Graph calls instead.

Entra • created

Agent ID blueprint

Parent application and credential boundary. Its principal exists in the tenant. One blueprint can create or act for multiple child Agent IDs.

Entra • created

Child Agent ID

The distinct workload identity for incident-adviser. Its object ID appears in the resource token; the API role is assigned to this child.

Azure • created

UAMI

User-assigned managed identity intended as the Pod's secretless credential bridge to the blueprint. It does not carry the MCP API role.

Kubernetes • proposed

ServiceAccount + Pod

The ServiceAccount identifies the Pod to AKS Workload Identity. Its annotation points to the UAMI client ID, not the child Agent ID.

Authorization • created

API role + Gateway

The test API defines team-event.mcp.use; the child receives it. The proposed Gateway policy checks token audience and role before the MCP route.

Not interchangeable: Azure RBAC controls Azure resources; Kubernetes RBAC controls cluster operations; an Entra app role in the Agent ID's API token controls this MCP call.

04 / partly proved

Federation

A dedicated UAMI and UAMI → blueprint trust exist. The AKS ServiceAccount → UAMI trust needs a cluster issuer and is absent.

05 / rendered only

GitOps manifest

A validator can render a private overlay from a proposed AACM response. It has not called AACM or deployed a workload.

The annotation carrying the child ID is a mapping, not a credential. It helps correlate an agent manifest with its Entra object; it does not, by itself, make the Pod authenticate as that Agent ID.

03 / in the AKS manifest

Two trust links, one still missing

On the ServiceAccount

azure.workload.identity/client-id = UAMI client ID. The Pod also needs azure.workload.identity/use: "true".

FIC #1 on UAMI

Would trust the chosen cluster's OIDC issuer, exact system:serviceaccount:team-event:incident-adviser-id subject, and token-exchange audience. No cluster exists in this subscription, so this was not created.

FIC #2 on blueprint

Already configured to trust the UAMI's Entra principal ID as subject, with Entra as issuer and the token-exchange audience. Its fields were read back; the UAMI exchange itself is not yet exercised.

06 / decisions before a work rollout

The next three ownership questions

Identity / AACM owner

What does AACM actually expose?

Confirm the blueprint approval process, real request/response schema, Agent ID lifecycle, sponsors, and exact app-role assignments. Replace the sample contract with the real integration only after review.

AKS / platform owner

Who completes FIC #1?

Choose the existing cluster, OIDC issuer, ServiceAccount, namespace, and UAMI ownership. Enable the Workload ID label and verify the Pod obtains a UAMI assertion.

kagent / gateway owner

Who gets and refreshes the token?

Choose a proven token helper or Gateway capability. Verify a child Agent ID token reaches MCP, renews before expiry, and is rejected for wrong audience, role, or agent.

Security boundary: a blueprint credential can potentially act for multiple children. Putting one shared credential in tenant Pods without an enforced child binding would undermine per-agent isolation. The design needs a trusted broker or narrower credential boundary before scaling.

For the work agent, start with the PoC handoff and the agent-side walkthrough. Keep the Azure/Entra and Kubernetes approvals separate.
