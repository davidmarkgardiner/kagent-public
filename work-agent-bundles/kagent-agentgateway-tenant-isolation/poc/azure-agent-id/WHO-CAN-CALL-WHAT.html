Who may call the agent? What may the agent call?

Treat these as two separate doors. An application Pod can use its existing AKS Workload Identity pattern to get an A2A-audience token for the agent. Entra issues that token; agentgateway makes the per-request allow/deny decision. The agent later uses its own blueprint-backed identity for MCP calls.

DOOR 1 · INBOUND

Caller → agent

Assign an invoke-agent A2A app role to the caller's Entra principal. An AKS application can obtain that API token through Workload Identity; the A2A gateway checks it before forwarding.

DOOR 2 · OUTBOUND

Agent → MCP/tool

Grant a separate use-MCP role to the runtime child Agent ID. The MCP gateway checks that identity and permits only selected tools.

Read left to right, then down

Two requests. Two decisions.

The application Pod uses its own UAMI or app principal as the caller. It does not receive the agent's blueprint credential. Entra issues an A2A token with its assigned role; agentgateway validates and authorizes each A2A request. The agent's separate child Agent ID token is for the MCP door.

EXISTING AKS PATTERN

Token for Azure

The Pod uses Workload Identity to request a token for an Azure resource. Azure RBAC governs what that caller can do at the resource.

THIS AGENT CALL

Token for A2A

The same federation pattern can request a different audience: the Event A2A API. Entra supplies the assigned invoke role; agentgateway enforces the A2A route policy. An ARM token is not an A2A token.

UAMI is fine as an A2A caller: the caller UAMI can receive the A2A API app-role assignment. This does not revive the failed ServiceAccount → UAMI → Agent ID blueprint chain. The agent runtime's direct ServiceAccount → blueprint federation is a separate flow.
Human versus app: this DAG follows the application-Pod path. A human signs in interactively and needs a user-context access token for the A2A API. If an application instead calls using one app-only token for all its users, the gateway can identify the application, not the individual human behind each request.
Where the infra blueprint fits

The blueprint is a credential bridge, not the whole access policy.

1 · AKS TRUST

Pod → blueprint

The AKS ServiceAccount's exact OIDC issuer and system:serviceaccount:namespace:name subject match a federated credential on the blueprint. The ServiceAccount annotation points to the blueprint client ID.

2 · RUNTIME IDENTITY

Blueprint → child Agent ID

The token holder obtains a token for its child Agent ID. A blueprint credential may select other children under that blueprint, so use a dedicated trust boundary or a broker that enforces the child choice.

3 · ACTUAL GRANTS

Caller and child get different roles

The A2A API defines agent.invoke for the caller UAMI/app principal. The MCP API defines mcp.use for the runtime child Agent ID. Declaring a permission on a blueprint is not itself a grant.

Separate Azure RBAC: if the MCP accesses Key Vault, AKS, or another Azure resource, its own execution identity needs the appropriate resource-scoped Azure role. The agent's permission to call an MCP does not automatically grant that Azure role. A direct agent-to-Azure call would require a separate grant to the agent identity.

What each team actually sets up

Entra issues the grants. AKS enforces the path.

INFRA ID / AACM TEAM
1
Approve dedicated blueprint, principal, child Agent ID, owner, and exact AKS federated issuer/ServiceAccount subject.
2
Define/reuse protected A2A and MCP API registrations, audiences, and app roles.
3
Assign the A2A role to each approved caller UAMI/app/service principal; assign the MCP role to the runtime child Agent ID. Return IDs and read-back privately.
AKS / PLATFORM TEAM
1
For an AKS caller, bind its Pod ServiceAccount to its own UAMI/app Workload Identity. Separately deploy the agent's dedicated blueprint-federated ServiceAccount through GitOps; restrict who can use or alter it.
2
Protect A2A and MCP routes with separate gateway policies. Check audience, role, and exact identity together; allow only approved tools.
3
Use NetworkPolicy to prevent backend bypass, review ReferenceGrants, and implement short-lived token renewal with expiry/fail-closed tests.
