01 · Actual mechanism

GitLab records the work. The poller owns the state.

Issue labels → scheduled poller → PM and delegated agents → independently checked GitLab evidence.

Two GitLab connections

Agents use the bundled fixed-project GitLab MCP. The poller uses GitLab REST directly to inspect artifacts, add checkpoint notes and change labels. A tool in the installer’s session does not automatically connect deployed agents.

Separate model route

Agents reach an approved model through agentgateway. The lab used Kimi; the workplace profile chooses its own model. The GitLab MCP path is direct in the supplied rig.

Each parent has one annotated child in the proven flow. Role assignment is A2A delegation, not GitLab user assignment. General multi-task planning is a future extension.

02 · Start the real run

The installer can create or tag the parent.

  1. Verify the exact sandbox repo, token identity, allowed files and green human-owned CI.
  2. Create a fresh issue from the demo template with measurable acceptance criteria.
  3. Add sdlc-rig-poc and agent:plan, preserving unrelated labels.
  4. Read the issue back and open its actual GitLab URL before enabling intake.
Installer MCP: gitlab_create_issue(title, description)
Then: gitlab_get_issue(iid)
Then: gitlab_update_issue(iid, labels = existing labels + intake labels)

The bundled create tool does not accept labels. Its update tool replaces the label array, so read and merge first. REST can instead use add_labels. Follow the runbook’s exact schemas and existing-issue checks.

The runtime PM does not get the label-update tool. It plans and delegates; the deterministic poller controls later labels. Use a new issue for each demonstration, not a stale branch or manually reset state.

Observe state changes

The poller removes the prior state label and adds the next one. GitLab’s label lists then show the issue in the matching column. Accepted stays an open issue; it is not the Closed list.

Keep transitions trustworthy

Do not drag cards into Build, Test, Review or Changes. Human-added intermediate state labels are blocked by the rig. The audience watches the workflow rather than advancing it.

Board behavior: GitLab issue-board documentation. Board setup APIs are not bundled MCP tools.

06 · Workplace rehearsal

Show the goal even when the target hits a blocker.

Observed symptom Next evidence to inspect
No pickup Exact labels, open issue, suspended CronJob, schedule and current Job.
No child or tools Model/A2A connectivity, MCP discovery, CA/proxy, policy and token identity.
Pods Pending Node placement, capacity, admission and image pulls.
CI waiting Current SHA, runner availability and job status.
Timed-out call Original agent task may still run. Pause; inspect it before replay.
Do not force a success for the audience. Explain the last verified checkpoint, the blocker, and what the next check will prove. Keep the conceptual diagram visible while investigating.

Open hardening includes durable A2A task-status recovery, per-issue queue isolation, CI wait limits, independent tester artifacts and credential separation. Cluster-admin helps install resources; it does not establish runtime correctness.

07 · Destination

Two workflows, one reviewable delivery story.

Issue-board rig

Request → PM/worker collaboration → repository changes → green CI → reviewed draft MR. Installable sandbox assets exist. Show this live after target rehearsal.

Pipeline quality gate

MR → authenticated endpoint → agent review/test proposals → isolated tests → mandatory GitLab merge gate. Bridge and test executor still need target implementation.

Both retain human merge approval. The separate pipeline gate must prove expected baseline assertion failure and candidate success before its generated tests count as merge evidence.
